# Expo and Native Builds

> What actually happens when you run this app, why `android/` is not in git, and the one question you will ask every day — *do I need to rebuild?* Read this if you have never shipped a mobile app. The step-by-step first run is [run-the-app-on-an-android-emulator.md](../tutorials/run-the-app-on-an-android-emulator.md).

## Context

On the web, "run the app" means one thing: a dev server serves your code and the browser
loads it. Refresh, and you are looking at your change.

A React Native app is not one thing. It is **two artefacts that are built by different
tools, at different times, and updated by different commands.** Almost every confusing
half-hour a mobile beginner loses is the same confusion: a change was made to one artefact
while the other one — the stale one — was the thing on screen.

So the mental model below is not trivia. It is the thing that tells you whether to press
`r` and wait two seconds or run a command and wait twelve minutes.

## Structure

```text
┌─────────────────────────────────────────────────────────────────┐
│  Your machine                                                   │
│                                                                 │
│   app/  src/  assets/          ──► Metro (the JS bundler)       │
│   TypeScript, React                    │                        │
│                                        │ serves the JS bundle   │
│   app.config.ts                        │ over the network       │
│   package.json (native deps)           │                        │
│         │                              │                        │
│         │ expo prebuild                │                        │
│         ▼                              │                        │
│   android/  ios/               ──► Gradle / Xcode               │
│   generated native project             │                        │
│                                        │ builds a binary        │
└────────────────────────────────────────┼────────────────────────┘
                                         ▼
                        ┌────────────────────────────────┐
                        │  Emulator / phone              │
                        │                                │
                        │  the installed app (the shell) │
                        │    + JS bundle (the contents)  │
                        └────────────────────────────────┘
```

**The shell** is a real Android or iOS app: Java/Kotlin and C++, compiled by Gradle,
installed as an APK. It contains every native capability the app can ever use — the camera,
GPS, the Naver map SDK, Firebase, the storage engine. Adding a capability means building a
new shell.

**The contents** are your TypeScript, bundled by Metro into JavaScript. The shell downloads
it from Metro at launch in development, and has it baked in for release. Changing a screen
changes only this.

That asymmetry is the whole story. **Screen work is cheap. Capability work is expensive.**

## What Expo is, and is not

Expo is not an alternative to React Native — it is a toolkit layered on top of it. Three
parts matter here:

| Part | What it is | Where you see it in this repo |
| --- | --- | --- |
| **The SDK** | A library of native modules with one JS API each — `expo-camera`, `expo-location`, `expo-image-picker` | The `expo-*` entries in `package.json` |
| **The CLI** | The commands that bundle, generate and build — `expo start`, `expo prebuild`, `expo run:android` | The `scripts` block in `package.json` |
| **Config plugins** | Code that edits the native project during generation, so you never edit it by hand | The `plugins` array in `app.config.ts` |

A **config plugin** is the piece most worth understanding, because it is why this repo has
no native code in it. When `app.config.ts` says:

```ts
[
  'expo-camera',
  {
    cameraPermission: '촬영지에서 사진을 찍어 티켓을 발행하기 위해 카메라를 사용합니다.',
    recordAudioAndroid: false,
  },
],
```

…that Korean sentence is not decoration. At generation time the plugin writes it into
`AndroidManifest.xml` and `Info.plist` as the permission prompt the OS shows the user. The
declaration lives in TypeScript; the native file is an output.

## Continuous Native Generation

Look at `.gitignore`:

```text
# Native builds (CNG — regenerated by expo prebuild)
/ios
/android
```

**The native projects are not in version control.** A fresh clone has no `android/`
directory at all. This is deliberate, and it is called **CNG — Continuous Native
Generation**.

`npx expo prebuild` reads `app.config.ts` and `package.json` and *generates* `android/` and
`ios/` from scratch. `yarn android` runs it for you when the directory is missing, which is
why the first run of a fresh clone takes so much longer than the second.

The trade is worth stating plainly:

- **What you gain.** Nobody merges a conflict in `build.gradle`. Upgrading Expo does not
  mean hand-patching native files. Every native setting is one declaration in one
  TypeScript file, reviewable in a diff.
- **What you give up.** You cannot edit `android/` or `ios/`. Anything you write there is
  deleted by the next `prebuild --clean` without warning. Native changes go in
  `app.config.ts` — through a plugin, or through `expo-build-properties`.

> [!WARNING]
> Two version numbers live in `app.config.ts` for exactly this reason: `ios.buildNumber`
> and `android.versionCode`. Their natural homes — `Info.plist` and `build.gradle` — are
> regenerated, so a number kept there is silently reset, and the next person to upload
> finds out from a store rejection. The comments around them in `app.config.ts` say so.

## When do I need to rebuild?

This is the table to keep open. Read it as: *how deep did my change go?*

| You changed | What it really is | What to do |
| --- | --- | --- |
| A `.tsx` / `.ts` file in `app/` or `src/` | JavaScript | **Nothing.** Fast Refresh already applied it |
| Same, but the screen looks wrong or state got stuck | JavaScript | Press `r` in the Metro terminal to reload |
| An image or font in `assets/` | Bundled by Metro | Restart Metro: `yarn start --clear` |
| **Anything in `.env`** — including `EXPO_PUBLIC_USE_MOCKS` | Baked into the binary at build time. Metro does **not** serve it | `yarn android`. See the warning below |
| `EXPO_PUBLIC_NAVER_MAP_CLIENT_ID` | That, *and* a config plugin writes it into the native manifest | `npx expo prebuild -p android --clean`, then `yarn android` |
| `package.json` — any dependency added, removed or bumped | It may carry native code | `yarn install`, then `yarn android` |
| `app.config.ts` — `plugins`, `permissions`, `infoPlist`, icons, splash | Native project configuration | `npx expo prebuild -p android --clean`, then `yarn android` |
| `google-services.json` arrived or changed | Native Firebase config | `npx expo prebuild -p android --clean`, then `yarn android` |

Two rules of thumb cover everything not in the table:

1. **If the change is visible in a diff of a `.tsx` file, it is free.** Save and look.
2. **If the change is in `package.json`, `app.config.ts` or `.env`, assume it needs a
   rebuild.** A rebuild you did not need costs ten minutes. A rebuild you skipped costs an
   afternoon of debugging an app that does not match its own source.

> [!WARNING]
> The `.env` row surprises everyone, so it is worth knowing the mechanism. No runtime code
> in this repo reads `process.env` — check for yourself, there are no matches under `src/`
> or `app/`. Values travel `.env` → `app.config.ts` → `extra` → `Constants.expoConfig.extra`
> → `AppConfig` in `src/lib/config.ts`, which is the single consumer. That `extra` object is
> compiled into the app binary, and **the dev server's manifest serves `extra: null`** — so
> restarting Metro, even with `--clear`, changes nothing. Flipping `EXPO_PUBLIC_USE_MOCKS`
> between fixtures and live Firebase is a native rebuild every time.
>
> To check which side is actually live, watch the Metro log the first time a screen loads
> data: it names either `src/lib/repositories/mock.ts` or `src/lib/repositories/firebase.ts`.
> That is the ground truth, not what `.env` says.

> [!WARNING]
> Rule 2 is written from this repo's own history, twice. Build 12 added
> `@shopify/react-native-skia` — a native dependency — and the JS referenced a module the
> installed binary did not contain, so 티켓 crashed on device only. Build 13 added an
> `ios.infoPlist` key without a prebuild, so the permission string never reached the
> binary and iOS killed the app the first time a tester opened the photo picker. **Neither
> was caught by typecheck, lint, or a green build.** The full accounts are in the
> `ios.buildNumber` comment in `app.config.ts`.

## Why this app cannot use Expo Go

Most Expo tutorials tell you to install **Expo Go**, scan a QR code, and start coding. That
will not work here, and it is worth knowing why so the advice does not keep tempting you.

Expo Go is a single pre-built app on the store containing the native modules of the standard
Expo SDK. Your JS is loaded into somebody else's shell. That is a fine deal — until your app
needs a native module that shell does not have.

This one needs several:

| Dependency | Why Expo Go cannot host it |
| --- | --- |
| `@mj-studio/react-native-naver-map` | Third-party native map SDK, from Naver's own Maven repository |
| `@react-native-firebase/*` | Native Firebase SDKs, keyed to `com.zoyoong.pindom` |
| `react-native-mmkv` + `react-native-nitro-modules` | Native C++ storage engine |
| `@shopify/react-native-skia` | Native graphics engine, for the 홀로그램 ticket |

So this project uses a **development build** instead: the same app shell you would ship,
compiled from *this* repo's dependencies, but pointed at Metro on your machine so JS still
hot-reloads. You get every convenience of Expo Go. You just have to build the shell
yourself, once, and again whenever the native surface changes.

> [!NOTE]
> If you find a Stack Overflow answer, a blog post or a Claude reply that says "just run
> `npx expo start` and open it in Expo Go", it is answering a different question. The
> command for this repo is `yarn android`.

## Keywords

Say these words when you ask Claude for help, and you will get an answer about this stack
instead of a generic React one. Vague questions produce web-React answers; these terms are
what make an answer land in the right layer.

### The two artefacts

| Term | Meaning |
| --- | --- |
| **JS bundle** | Your TypeScript, compiled and packed into one JavaScript file |
| **Metro** | The bundler and dev server that makes it. The terminal window you leave running |
| **Fast Refresh** | Metro pushing an edited module into the running app, keeping component state |
| **Native build** | Compiling the app shell with Gradle (Android) or Xcode (iOS) |
| **Hermes** | The JS engine inside the app. Not V8 — so a Node or browser answer may not apply |
| **New Architecture / Fabric / TurboModules** | React Native's current native bridge. Enabled here via `newArchEnabled` in `app.config.ts`. Say it when a library says it is incompatible |

### Getting the shell built

| Term | Meaning |
| --- | --- |
| **prebuild** | `npx expo prebuild` — generating `android/` and `ios/` from `app.config.ts` |
| **CNG** | Continuous Native Generation. The policy of treating those folders as build output |
| **config plugin** | A function that edits the generated native project. The `plugins` array |
| **autolinking** | Native dependencies in `package.json` wiring themselves into the build with no manual step |
| **development build** | The debuggable app shell you install on the emulator. This repo's normal way to run |
| **Expo Go** | The generic sandbox app. **Not usable here** — see above |
| **EAS Build / EAS Submit** | Expo's cloud builders and store uploader. Configured in `eas.json` |
| **Gradle / AVD / adb / APK** | Android's build tool, virtual device, device-control CLI, and app package format |

### This repo specifically

| Term | Meaning |
| --- | --- |
| **expo-router** | File-based routing. A file at `app/place/[id].tsx` *is* the route `/place/:id` |
| **typed routes** | `experiments.typedRoutes` — route strings are typechecked, so a typo fails `yarn typecheck` |
| **repository boundary** | Screens read data only from `src/lib/repositories/`, never from Firebase directly ([ADR 0005](../decisions/0005-keep-firebase-behind-a-repository-boundary.md)) |
| **fixtures / mocks** | `src/mocks/` — typed fake data the repositories serve when `EXPO_PUBLIC_USE_MOCKS` is `true` |
| **design tokens** | The only legal source of colour, spacing and type. A raw hex in a screen is a bug ([design-tokens.md](../reference/design-tokens.md)) |

A question that works:

> This is an Expo SDK app with the New Architecture on, using a development build (not Expo
> Go) with CNG — `android/` is gitignored and generated by prebuild. I added a native
> dependency and the app crashes on launch. What should I check?

A question that does not:

> My React app crashes.

## Looking things up

Knowing where to search matters more than knowing the answer. For this stack, the hard part
is not finding results — it is **throwing the wrong ones away**. Most React Native material
online describes a setup this repo does not use, and none of it says so.

### Where to search, in order

| Source | Use it for | Note |
| --- | --- | --- |
| [Expo documentation](https://docs.expo.dev) | Anything `expo-*`, config plugins, prebuild, development builds, EAS | **Set the version selector** to the SDK in `package.json`. Expo's docs change materially between SDKs |
| [React Native documentation](https://reactnative.dev) | Core components and APIs — `View`, `Text`, `FlatList`, `StyleSheet`, `Animated` | The version dropdown matters here too |
| [Android developer documentation](https://developer.android.com/studio/run/emulator) | The emulator, AVDs, `adb` | Independent of React Native, so it never goes stale in the same way |
| The library's own repository | A third-party native module misbehaving | See the table below for which ones this repo has |
| GitHub **Issues** search on the owning repo | An exact error string | Usually the only place a real build error is discussed. Search the error text in quotes, and include closed issues |
| Stack Overflow | Last resort | Check the date. An accepted answer from before the New Architecture is often actively wrong |

### The third-party natives in this app

When one of these breaks, the answer is in its own repository, not in Expo's docs:

| Package | Where to look |
| --- | --- |
| `@mj-studio/react-native-naver-map` | Its GitHub repository. Naver's own SDK docs are Korean and cover the native SDK, not this wrapper |
| `@react-native-firebase/*` | [rnfirebase.io](https://rnfirebase.io) — and note this repo reaches Firebase only through `src/lib/repositories/` |
| `@shopify/react-native-skia` | Its documentation site and GitHub issues |
| `react-native-mmkv`, `react-native-nitro-modules` | Their GitHub repositories |
| `expo-router` | The Expo documentation, under Router |

### How to tell an answer does not apply

This is the filter that saves the most time. If a result says any of the following, it is
describing a different kind of project:

| The answer says | Verdict | Why |
| --- | --- | --- |
| "Open it in Expo Go", "scan the QR code" | **Does not apply** | This app needs a development build |
| "Run `react-native init`", "the bare workflow" | **Usually does not apply** | That is a hand-maintained native project. This one is generated |
| "Edit `android/build.gradle`" or `AndroidManifest.xml` | **Does not apply as written** | Those files are prebuild output. The change belongs in `app.config.ts` |
| "Run `react-native link`" | **Obsolete** | Autolinking replaced it years ago |
| "Edit `app.json`" | **Adapt it** | The same settings live in `app.config.ts` here, in TypeScript |
| "Disable the New Architecture" | **Check first** | It is on in `app.config.ts`. Turning it off is a project-wide decision, not a fix |
| Anything about `expo eject` | **Obsolete** | Replaced by `expo prebuild` |

### Search phrasings that work

- Put the **exact error text in quotes**, plus the library name:
  `"Unsupported class file major version" expo android`
- Name the mechanism, not the symptom: `expo config plugin android permission` beats
  `how to add permission react native`.
- For an Expo API, prefix the site: `site:docs.expo.dev expo-location background`
- For a native crash, search the owning repository's issues for the top line of the stack
  trace, not your own description of it.

> [!NOTE]
> The same filter applies to answers from Claude. Give it the context from
> [Keywords](#keywords) — development build, CNG, prebuild, New Architecture — and it will
> answer about this stack. Leave that out and you will get advice for a `react-native init`
> project, confidently.
