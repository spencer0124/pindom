# Expo와 네이티브 빌드

> 이 앱을 실행하면 실제로 무슨 일이 벌어지는지, `android/`가 왜 git에 없는지, 그리고 매일 하게 될 질문 하나 — *리빌드해야 하나?* 모바일 앱을 만들어본 적 없다면 이 문서를 읽으세요. 단계별 첫 실행은 [run-the-app-on-an-android-emulator.ko.md](../tutorials/run-the-app-on-an-android-emulator.ko.md)에 있습니다.

> [!NOTE]
> 이 문서는 [expo-and-native-builds.md](expo-and-native-builds.md)의 한국어판입니다.
> 두 문서가 어긋나면 **영문판이 기준**입니다 ([docs/README.md](../README.md) §6).

## 배경

웹에서 "앱을 실행한다"는 건 하나를 뜻합니다. 개발 서버가 코드를 서빙하고 브라우저가 그걸 로드하죠.
새로고침하면 내가 바꾼 게 보입니다.

React Native 앱은 하나가 아닙니다. **서로 다른 도구가, 서로 다른 시점에 만들고, 서로 다른 명령으로
갱신하는 산출물 두 개**입니다. 모바일 초보가 30분씩 날리는 상황은 거의 항상 같은 혼동입니다. 한쪽
산출물을 고쳤는데, 화면에 떠 있는 건 갱신 안 된 다른 쪽인 거예요.

그래서 아래 모델은 잡지식이 아닙니다. `r` 누르고 2초 기다릴 일인지, 명령어 치고 12분 기다릴 일인지를
알려주는 게 이겁니다.

## 구조

```text
┌─────────────────────────────────────────────────────────────────┐
│  내 컴퓨터                                                       │
│                                                                 │
│   app/  src/  assets/          ──► Metro (JS 번들러)             │
│   TypeScript, React                    │                        │
│                                        │ JS 번들을 네트워크로     │
│   app.config.ts                        │ 서빙                    │
│   package.json (네이티브 의존성)         │                        │
│         │                              │                        │
│         │ expo prebuild                │                        │
│         ▼                              │                        │
│   android/  ios/               ──► Gradle / Xcode               │
│   생성된 네이티브 프로젝트                │                        │
│                                        │ 바이너리를 빌드          │
└────────────────────────────────────────┼────────────────────────┘
                                         ▼
                        ┌────────────────────────────────┐
                        │  에뮬레이터 / 실기기            │
                        │                                │
                        │  설치된 앱 (껍데기)             │
                        │    + JS 번들 (내용물)           │
                        └────────────────────────────────┘
```

**껍데기**는 진짜 안드로이드/iOS 앱입니다. Java·Kotlin·C++로 되어 있고, Gradle이 컴파일해서
APK로 설치됩니다. 앱이 앞으로 쓸 수 있는 모든 네이티브 능력이 여기 들어 있습니다 — 카메라, GPS,
네이버 지도 SDK, Firebase, 저장소 엔진. **능력을 추가한다는 건 껍데기를 새로 만든다는 뜻입니다.**

**내용물**은 여러분의 TypeScript입니다. Metro가 JavaScript로 번들링합니다. 개발 중에는 앱이 실행될
때 Metro에서 받아오고, 릴리스에서는 안에 구워져 있습니다. **화면을 고치는 건 이쪽만 바꿉니다.**

이 비대칭이 전부입니다. **화면 작업은 싸다. 능력 작업은 비싸다.**

## Expo란 무엇이고, 무엇이 아닌가

Expo는 React Native의 대안이 아닙니다. **React Native 위에 얹힌 도구 모음**입니다. 여기서 중요한
건 세 부분입니다.

| 구성 | 정체 | 이 repo에서 보이는 곳 |
| --- | --- | --- |
| **SDK** | 네이티브 모듈마다 JS API를 하나씩 붙여둔 라이브러리 모음 — `expo-camera`, `expo-location`, `expo-image-picker` | `package.json`의 `expo-*` 항목들 |
| **CLI** | 번들·생성·빌드를 하는 명령어들 — `expo start`, `expo prebuild`, `expo run:android` | `package.json`의 `scripts` 블록 |
| **Config plugin** | 생성 시점에 네이티브 프로젝트를 고쳐주는 코드. 덕분에 네이티브 파일을 직접 손댈 일이 없습니다 | `app.config.ts`의 `plugins` 배열 |

**config plugin**이 제일 알아둘 값어치가 있습니다. 이 repo에 네이티브 코드가 하나도 없는 이유가
이거거든요. `app.config.ts`에 이렇게 적혀 있으면:

```ts
[
  'expo-camera',
  {
    cameraPermission: '촬영지에서 사진을 찍어 티켓을 발행하기 위해 카메라를 사용합니다.',
    recordAudioAndroid: false,
  },
],
```

이 한국어 문장은 장식이 아닙니다. 생성 시점에 플러그인이 이걸 `AndroidManifest.xml`과
`Info.plist`에 써넣고, OS가 사용자에게 보여주는 권한 요청 문구가 됩니다. **선언은 TypeScript에
살고, 네이티브 파일은 그 결과물입니다.**

## Continuous Native Generation (CNG)

`.gitignore`를 보세요.

```text
# Native builds (CNG — regenerated by expo prebuild)
/ios
/android
```

**네이티브 프로젝트는 버전 관리에 안 들어갑니다.** 새로 clone하면 `android/` 디렉터리가 아예 없습니다.
이건 의도된 거고, **CNG(Continuous Native Generation)** 라고 부릅니다.

`npx expo prebuild`가 `app.config.ts`와 `package.json`을 읽어 `android/`와 `ios/`를 **처음부터
생성**합니다. 디렉터리가 없으면 `yarn android`가 알아서 이걸 먼저 돌리는데, 새로 clone한 뒤 첫
실행이 두 번째보다 훨씬 오래 걸리는 이유가 그겁니다.

득실을 분명히 해두면:

- **얻는 것.** `build.gradle` 충돌을 머지할 일이 없습니다. Expo 업그레이드가 네이티브 파일 수동
  패치를 뜻하지 않습니다. 모든 네이티브 설정이 TypeScript 파일 하나 안의 선언 하나이고, diff로
  리뷰됩니다.
- **잃는 것.** `android/`나 `ios/`를 편집할 수 없습니다. 거기 쓴 건 다음 `prebuild --clean` 때
  경고 없이 지워집니다. 네이티브 변경은 `app.config.ts`에서 — plugin을 통하거나,
  `expo-build-properties`를 통해서 합니다.

> [!WARNING]
> `app.config.ts`에 버전 번호 두 개가 사는 이유가 정확히 이겁니다: `ios.buildNumber`와
> `android.versionCode`. 원래 있어야 할 자리인 `Info.plist`와 `build.gradle`은 재생성되니까,
> 거기 적어둔 숫자는 조용히 초기화되고, 다음에 업로드하는 사람이 스토어 거절로 그 사실을 알게 됩니다.
> `app.config.ts`의 해당 주석에 그렇게 적혀 있습니다.

## 언제 리빌드해야 하나?

계속 열어둘 표입니다. *내 변경이 얼마나 깊이 들어갔나?* 로 읽으세요.

| 바꾼 것 | 실제 정체 | 할 일 |
| --- | --- | --- |
| `app/`이나 `src/`의 `.tsx` / `.ts` 파일 | JavaScript | **아무것도.** Fast Refresh가 이미 반영했습니다 |
| 위와 같은데 화면이 이상하거나 상태가 꼬였을 때 | JavaScript | Metro 터미널에서 `r` |
| `assets/`의 이미지나 폰트 | Metro가 번들링 | Metro 재시작: `yarn start --clear` |
| **`.env`의 무엇이든** — `EXPO_PUBLIC_USE_MOCKS` 포함 | 빌드 시점에 바이너리에 구워짐. Metro가 주는 게 **아님** | `yarn android`. 아래 경고 참고 |
| `EXPO_PUBLIC_NAVER_MAP_CLIENT_ID` | 위와 같고, *게다가* config plugin이 네이티브 매니페스트에도 씀 | `npx expo prebuild -p android --clean` 후 `yarn android` |
| `package.json` — 의존성 추가·삭제·버전 변경 | 네이티브 코드를 품고 있을 수 있음 | `yarn install` 후 `yarn android` |
| `app.config.ts` — `plugins`, `permissions`, `infoPlist`, 아이콘, 스플래시 | 네이티브 프로젝트 설정 | `npx expo prebuild -p android --clean` 후 `yarn android` |
| `google-services.json`이 새로 생기거나 바뀜 | 네이티브 Firebase 설정 | `npx expo prebuild -p android --clean` 후 `yarn android` |

표에 없는 건 이 두 가지로 커버됩니다.

1. **`.tsx` 파일의 diff에 보이는 변경이면 공짜다.** 저장하고 보면 됩니다.
2. **`package.json`, `app.config.ts`, `.env`의 변경이면 리빌드가 필요하다고 가정한다.** 안 해도
   될 리빌드를 한 대가는 10분입니다. 해야 할 리빌드를 건너뛴 대가는, 자기 소스와 일치하지 않는 앱을
   디버깅하는 반나절입니다.

> [!WARNING]
> `.env` 줄은 다들 놀라는 부분이라 원리를 알아둘 값어치가 있습니다. 이 repo의 런타임 코드는
> `process.env`를 읽는 곳이 **하나도 없습니다** — 직접 확인해 보세요, `src/`와 `app/` 아래에 검색
> 결과가 없습니다. 값은 `.env` → `app.config.ts` → `extra` → `Constants.expoConfig.extra` →
> `src/lib/config.ts`의 `AppConfig` 순서로 흐르고, 마지막이 유일한 소비자입니다. 그 `extra` 객체는
> **앱 바이너리에 컴파일되어 들어가고, 개발 서버의 manifest는 `extra: null`을 줍니다.** 그래서
> Metro를 `--clear`로 재시작해도 아무것도 안 바뀝니다. `EXPO_PUBLIC_USE_MOCKS`를 픽스처와 실제
> Firebase 사이에서 뒤집는 건 매번 네이티브 리빌드입니다.
>
> 지금 어느 쪽이 살아 있는지 확인하려면, 화면이 처음 데이터를 로드할 때 Metro 로그를 보세요.
> `src/lib/repositories/mock.ts` 또는 `src/lib/repositories/firebase.ts` 중 하나를 찍습니다.
> `.env`에 뭐라고 써 있느냐가 아니라 **그게 사실**입니다.

> [!WARNING]
> 규칙 2는 이 repo가 직접 두 번 겪고 쓴 겁니다. Build 12는 네이티브 의존성인
> `@shopify/react-native-skia`를 추가했는데, JS가 설치된 바이너리에 없는 모듈을 참조해서 티켓이
> **실기기에서만** 죽었습니다. Build 13은 prebuild 없이 `ios.infoPlist` 키를 추가해서, 권한 문구가
> 바이너리까지 가지 못했고 테스터가 사진 선택기를 처음 여는 순간 iOS가 앱을 죽였습니다.
> **둘 다 typecheck·lint·초록 빌드 어느 것도 못 잡았습니다.** 전체 경위는 `app.config.ts`의
> `ios.buildNumber` 주석에 있습니다.

## 이 앱이 Expo Go를 쓸 수 없는 이유

Expo 튜토리얼 대부분은 **Expo Go**를 깔고, QR 코드를 찍고, 바로 코딩을 시작하라고 합니다. 여기서는
그게 안 됩니다. 그 조언이 계속 눈에 밟힐 테니 이유를 알아두는 게 좋습니다.

Expo Go는 스토어에 올라와 있는 **미리 빌드된 앱 하나**이고, 표준 Expo SDK의 네이티브 모듈들을
담고 있습니다. 내 JS가 남의 껍데기 안에 로드되는 구조예요. 나쁘지 않은 거래입니다 — 그 껍데기에 없는
네이티브 모듈이 필요해지기 전까지는.

이 앱은 여러 개가 필요합니다.

| 의존성 | Expo Go가 못 담는 이유 |
| --- | --- |
| `@mj-studio/react-native-naver-map` | 서드파티 네이티브 지도 SDK, 네이버 자체 Maven 저장소에서 받음 |
| `@react-native-firebase/*` | 네이티브 Firebase SDK, `com.zoyoong.pindom`에 묶여 있음 |
| `react-native-mmkv` + `react-native-nitro-modules` | 네이티브 C++ 저장소 엔진 |
| `@shopify/react-native-skia` | 네이티브 그래픽 엔진, 홀로그램 티켓용 |

그래서 이 프로젝트는 대신 **development build**를 씁니다. 실제로 출시할 것과 같은 앱 껍데기를 *이*
repo의 의존성으로 컴파일하되, 내 컴퓨터의 Metro를 바라보게 해서 JS는 그대로 hot reload 되게 하는
방식입니다. Expo Go의 편의는 전부 그대로 얻습니다. 껍데기를 한 번 직접 빌드해야 하고, 네이티브
표면이 바뀔 때 다시 빌드해야 할 뿐입니다.

> [!NOTE]
> Stack Overflow 답변이든 블로그 글이든 Claude 답변이든, "그냥 `npx expo start` 돌리고 Expo Go에서
> 열면 된다"고 하면 그건 **다른 질문에 답하고 있는 겁니다.** 이 repo의 명령은 `yarn android`입니다.

## 키워드

Claude에게 물어볼 때 아래 단어들을 쓰면, 일반적인 React 답변 대신 이 스택에 대한 답이 옵니다.
두루뭉술한 질문은 웹 React 답변을 부르고, 이 용어들이 답을 제 계층에 꽂아줍니다.

### 두 개의 산출물

| 용어 | 뜻 |
| --- | --- |
| **JS bundle** | 내 TypeScript가 컴파일·압축돼 하나로 묶인 JavaScript 파일 |
| **Metro** | 그걸 만드는 번들러이자 개발 서버. 계속 켜두는 그 터미널 창 |
| **Fast Refresh** | Metro가 수정된 모듈만 실행 중인 앱에 밀어넣는 것. 컴포넌트 상태는 유지됨 |
| **Native build** | Gradle(안드로이드)이나 Xcode(iOS)로 앱 껍데기를 컴파일하는 것 |
| **Hermes** | 앱 안에 들어 있는 JS 엔진. V8이 아니라서, Node나 브라우저 기준 답변이 안 맞을 수 있음 |
| **New Architecture / Fabric / TurboModules** | React Native의 현행 네이티브 브릿지. `app.config.ts`의 `newArchEnabled`로 켜져 있음. 라이브러리가 호환이 안 된다고 할 때 꺼낼 단어 |

### 껍데기를 빌드하는 것들

| 용어 | 뜻 |
| --- | --- |
| **prebuild** | `npx expo prebuild` — `app.config.ts`로부터 `android/`, `ios/`를 생성하는 것 |
| **CNG** | Continuous Native Generation. 그 폴더들을 빌드 산출물로 취급하는 방침 |
| **config plugin** | 생성된 네이티브 프로젝트를 고치는 함수. `plugins` 배열 |
| **autolinking** | `package.json`의 네이티브 의존성이 수동 작업 없이 알아서 빌드에 연결되는 것 |
| **development build** | 에뮬레이터에 설치하는 디버그 가능한 앱 껍데기. 이 repo의 기본 실행 방식 |
| **Expo Go** | 범용 샌드박스 앱. **여기서는 못 씁니다** — 위 참고 |
| **EAS Build / EAS Submit** | Expo의 클라우드 빌더와 스토어 업로더. `eas.json`에 설정돼 있음 |
| **Gradle / AVD / adb / APK** | 안드로이드의 빌드 도구, 가상 기기, 기기 제어 CLI, 앱 패키지 형식 |

### 이 repo 고유

| 용어 | 뜻 |
| --- | --- |
| **expo-router** | 파일 기반 라우팅. `app/place/[id].tsx` 파일이 곧 `/place/:id` 라우트 |
| **typed routes** | `experiments.typedRoutes` — 라우트 문자열이 타입 체크돼서, 오타는 `yarn typecheck`에서 잡힘 |
| **repository boundary** | 화면은 `src/lib/repositories/`에서만 데이터를 읽고, Firebase를 직접 부르지 않음 ([ADR 0005](../decisions/0005-keep-firebase-behind-a-repository-boundary.md)) |
| **fixtures / mocks** | `src/mocks/` — `EXPO_PUBLIC_USE_MOCKS`가 `true`일 때 repository가 내주는 타입 있는 가짜 데이터 |
| **design tokens** | 색·간격·타이포의 유일한 합법적 출처. 화면 파일의 raw hex는 버그 ([design-tokens.md](../reference/design-tokens.md)) |

잘 되는 질문:

> Expo SDK 앱이고 New Architecture 켜져 있고, Expo Go가 아니라 development build를 씁니다.
> CNG라서 android/는 gitignore 되어 있고 prebuild로 생성됩니다. 네이티브 의존성을 추가했더니
> 실행하자마자 죽는데, 뭘 확인해야 하나요?

안 되는 질문:

> 제 React 앱이 죽어요.

## 찾아보는 법

답을 아는 것보다 **어디서 찾을지 아는 게** 더 중요합니다. 그리고 이 스택에서 어려운 건 결과를 찾는
게 아니라 **틀린 결과를 버리는 것**입니다. 인터넷의 React Native 자료 대부분은 이 repo가 쓰지 않는
구성을 설명하는데, 그렇다고 말해주지 않습니다.

### 어디를 먼저 볼 것인가

| 출처 | 쓸 곳 | 주의 |
| --- | --- | --- |
| [Expo 공식 문서](https://docs.expo.dev) | `expo-*` 전반, config plugin, prebuild, development build, EAS | **버전 선택기를 `package.json`의 SDK 버전으로 맞추세요.** Expo 문서는 SDK마다 내용이 실제로 달라집니다 |
| [React Native 공식 문서](https://reactnative.dev) | 코어 컴포넌트와 API — `View`, `Text`, `FlatList`, `StyleSheet`, `Animated` | 여기도 버전 드롭다운이 중요합니다 |
| [안드로이드 공식 문서](https://developer.android.com/studio/run/emulator) | 에뮬레이터, AVD, `adb` | React Native와 무관해서 같은 방식으로 낡지 않습니다 |
| 해당 라이브러리의 저장소 | 서드파티 네이티브 모듈이 말썽일 때 | 이 repo가 쓰는 것들은 아래 표 참고 |
| 그 저장소의 GitHub **Issues** 검색 | 정확한 에러 문구 | 실제 빌드 에러가 논의되는 거의 유일한 곳입니다. 에러 문구를 따옴표로 묶어 검색하고, 닫힌 이슈도 포함하세요 |
| Stack Overflow | 최후의 수단 | 날짜를 보세요. New Architecture 이전의 채택된 답변은 지금 오히려 틀린 경우가 많습니다 |

### 이 앱이 쓰는 서드파티 네이티브

아래 것들이 깨졌을 때 답은 Expo 문서가 아니라 각자의 저장소에 있습니다.

| 패키지 | 볼 곳 |
| --- | --- |
| `@mj-studio/react-native-naver-map` | 이 패키지의 GitHub 저장소. 네이버 공식 문서는 한국어지만 네이티브 SDK를 다루지, 이 래퍼를 다루지 않습니다 |
| `@react-native-firebase/*` | [rnfirebase.io](https://rnfirebase.io) — 다만 이 repo는 Firebase를 `src/lib/repositories/`를 통해서만 만집니다 |
| `@shopify/react-native-skia` | 공식 문서 사이트와 GitHub issues |
| `react-native-mmkv`, `react-native-nitro-modules` | 각자의 GitHub 저장소 |
| `expo-router` | Expo 공식 문서의 Router 섹션 |

### 그 답이 여기 적용되지 않는다는 신호

시간을 가장 많이 아껴주는 필터입니다. 검색 결과가 아래 중 하나를 말하고 있다면, 그건 다른 종류의
프로젝트를 설명하는 글입니다.

| 그 답이 하는 말 | 판정 | 이유 |
| --- | --- | --- |
| "Expo Go로 여세요", "QR 코드를 찍으세요" | **적용 안 됨** | 이 앱은 development build가 필요합니다 |
| "`react-native init`을 실행하세요", "bare workflow" | **대체로 적용 안 됨** | 그건 손으로 관리하는 네이티브 프로젝트입니다. 이건 생성되는 프로젝트고요 |
| "`android/build.gradle`을 수정하세요", `AndroidManifest.xml` 직접 수정 | **그대로는 적용 안 됨** | 그 파일들은 prebuild 산출물입니다. 변경은 `app.config.ts`에 들어가야 합니다 |
| "`react-native link`를 실행하세요" | **폐기됨** | 몇 년 전에 autolinking으로 대체됐습니다 |
| "`app.json`을 수정하세요" | **번역해서 적용** | 여기서는 같은 설정이 `app.config.ts`에 TypeScript로 들어 있습니다 |
| "New Architecture를 끄세요" | **먼저 확인** | `app.config.ts`에서 켜져 있습니다. 끄는 건 임시방편이 아니라 프로젝트 전체의 결정입니다 |
| `expo eject` 관련 내용 | **폐기됨** | `expo prebuild`로 대체됐습니다 |

### 잘 먹히는 검색어

- **에러 문구를 따옴표로 묶고** 라이브러리 이름을 붙이세요:
  `"Unsupported class file major version" expo android`
- 증상이 아니라 **메커니즘 이름**으로 검색하세요. `expo config plugin android permission`이
  `how to add permission react native`보다 훨씬 낫습니다.
- Expo API는 사이트를 지정하세요: `site:docs.expo.dev expo-location background`
- 네이티브 크래시는 내가 요약한 설명이 아니라 **스택 트레이스 맨 윗줄**을 해당 저장소 issues에서
  검색하세요.

> [!NOTE]
> 같은 필터가 Claude 답변에도 적용됩니다. [키워드](#키워드)의 맥락을 주세요 — development build,
> CNG, prebuild, New Architecture. 그러면 이 스택에 대한 답을 합니다. 그걸 빼면 `react-native init`
> 프로젝트용 조언이, 아주 자신 있게 돌아옵니다.
