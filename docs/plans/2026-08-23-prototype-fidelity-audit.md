# Prototype Fidelity Audit

> The evidence behind the [fidelity checklist](2026-08-23-prototype-fidelity-checklist.md): seven per-slice audits of the built screens against `design/2026-08-20-prototype.html`, one finding per row with the prototype value, the app value and a proposed fix. Read the checklist first; come here for the detail behind an ID.

## How it was produced

The prototype is a Claude Design canvas document: its `1a` flow is rendered markup with full
inline styles, and its state, gesture handlers and timers are a React class inside the
document's `text/x-dc` script. Each slice was read by one auditor against the same brief:
the two-axis rule from [design/README.md](../../design/README.md) — `2b` on colour, radius,
type and dividers; `1a` on layout, copy, flow, interaction and motion — with every deviation
already recorded in the `2026-08-22-*-slice-checklist.md` files treated as decided.

Finding IDs are per slice: the Discovery and Capture audits both number their rows `D-nn`,
and the Auth and Assistant audits both use `A-nn`. The checklist prefixes them with the
slice name to keep them apart.

Line references into the prototype point at the per-screen extracts the audit was run on
(`screens/is<Name>.html`, `proto.jsx`, `proto.css`), which were cut from the single HTML file
by splitting its `sc-if` blocks; the screen name is what matters, the line numbers are
approximate against the original file.

## Discovery — 홈 · 지도 · 장소/상세 · 탭바 · FAB

Slice: 홈 (`app/(tabs)/index.tsx`), 지도 (`app/(tabs)/map.tsx`), 장소/상세 (`app/place/[id].tsx`), the tab bar
(`app/(tabs)/_layout.tsx`) and the assistant FAB (`src/features/assistant/AssistantFab.tsx`).
Prototype sources: `screens/isHome.html`, `screens/isMap.html`, `screens/isPlace.html`, `screens/showTabs.html`,
`screens/showFab.html`, `proto.jsx`, `proto.css`. Checklists read first:
`docs/plans/2026-08-22-discovery-slice-checklist.md`, `docs/plans/2026-08-22-phase-2-3-checklist.md`.

Two facts about the prototype that shape the findings below:

- **There is no per-pin stagger.** `screens/isMap.html:17` applies `animation:pinDrop .5s cubic-bezier(.2,.9,.3,1) both`
  to every pin with no `animation-delay`, and `grep delay proto.jsx` returns nothing. All pins drop at once on entry.
- **`placeVisited` is hardcoded `true`** (`proto.jsx:1015`) and `reviewTag` starts as `'pose'` (`proto.jsx:624`).

### Big decisions (need the user)

1. **pinDrop on real tiles.** The Naver SDK rasterises a marker's custom child to an image on iOS, so the drop cannot be animated inside a marker. Options: (a) animate only the stand-in canvas (D-01) and accept static markers on tiles; (b) an RN overlay layer that projects lat/lng to screen on every camera event (`screenToLocation`/`locationToScreen` on the map ref) and animates pins there — faithful but a sizeable piece of work and it fights pan/zoom; (c) a cheap reveal on tiles: mount markers with `isHidden` and flip them visible after 500ms via state. Which?
2. **Where the map pin lives.** design-system.md lists "a map pin / place card" as a known gap that should land as a design-system component. D-02 proposes `src/features/discovery/MapPin.tsx`; promote it only if 장소/상세 or 추천 코스 also draws pins.
3. **Are 마감 임박 응모 per-최애?** 1a composes every raffle name with the selected 최애 (`proto.jsx:981-985`), so switching 최애 changes the block; the contract's `raffleRepository.list()` is global and has no artist key. D-08 keeps it global.
4. **홈's 응모하러 가기 target.** D-07 proposes the soonest open raffle, the rule the Tickets slice chose for 컬렉션; 1a opens the 응모 screen with no raffle pre-selected, which the app's `/raffle/[id]` cannot express.
5. **Short names in the contract.** 1a labels chips `BTS`, not `방탄소년단`, and pin captions `강릉`, not `주문진 방파제`. Neither `Artist.shortName` nor `Place.shortRegion` exists. Add them (backend owner) or accept the long forms.
6. **Camera framing with a fix.** D-03 proposes whole-country / fit-to-pins on entry as 1a does; the current nearby zoom is arguably more useful once a real tile is visible. Designer's call.
7. **The FAB's pink identity under 2b.** 1a's ring and glyph are a rose conic gradient (`#FFE1E8→#F8AEBB→#C8517A`) and the assistant's own screen carries the same aurora. Colour is 2b's axis, so D-20/21 propose the acid accent; if the assistant is meant to keep a distinct hue, that needs a token (`accentAssistant`) rather than raw hex.
8. **`workTitle` on 장소/상세.** D-15 restores 1a's `{최애} · {work kind} · {region}`; whether the work's title is worth a fourth segment (or its own line) is a copy decision 1a never made.

### Big decisions (need the user)
