# 앱·백엔드 점검 및 촬영 기능 변경

> 앱과 서버의 주요 경로를 점검한 결과, 이번 수정 내용, 배포 전 남은 작업을 기록한다.

## 점검 범위와 결론

앱의 라우팅·상태·repository 경계, 촬영·편집·발행, 인증·계정 전환, 공개 범위,
서버의 위치 판정·트랜잭션·보안 규칙·트리거·외부 API·탈퇴 정리, 테스트·의존성을 확인했다.
기존 서버 graphify 자료는 탐색에만 사용했고 현재 소스와 대조했다.
프로덕션의 데이터·요금·실측 지연·실제 배포 상태를 확인한 감사는 아니다.

기본 구조인 `app → features → repositories → Firebase`는 유지할 만하다.
화면·feature·디자인 시스템에서 Firebase 직접 import는 발견하지 않았다.
서버가 티켓 잔액과 위치 검증을 소유하고, 민감한 사용자 문서와 rate limit 문서를
규칙으로 닫는 구조도 적절하다. 반면 일부 정상 경로 위주의 테스트가 실제 우회를
정상 동작으로 인정하고 있었고, 공개 범위 전환의 비동기 처리에는 여전히 위험이 있다.

## 남은 우선순위

### P1 — 공개·비공개 전환의 트리거 순서와 토큰 회전

`syncGalleryOnVisibility`는 이벤트의 `after`만 보고 gallery를 덮어쓴다.
빠르게 public → private → public을 바꾸거나, 반대 순서의 이벤트가 늦게 도착하면
최종 ticket 상태와 gallery가 달라질 수 있다. 토큰 회전과 Firestore의 `photoUrl` 갱신도
서로 다른 시스템에서 진행되어 겹친 실행은 갤러리의 URL을 무효화할 수 있다.
스토리지 get 제한은 이 전체 문제를 해결하지 않는다.

다음 변경은 공개 범위 변경 callable에서 버전별 전환을 관리하고, gallery를 최신 ticket
상태로 수렴시키며, Storage 토큰 변경의 재시도·실패 복구까지 묶어야 한다.
지연·중복·역순 이벤트 테스트와 기존 URL의 무효화 테스트가 필요하다.
[Firestore 트리거 문서](https://firebase.google.com/docs/functions/firestore-events)는
이벤트 순서를 보장하지 않으며 중복 전달 가능성을 명시한다.

### P1 — 비용이 드는 호출에 App Check 미적용

Functions는 사용자별 일일 쿼터와 인스턴스 상한을 둔다. 그러나 App Check 연동이 없고
저장소의 `REQUIRE_EMAIL_VERIFIED` 값도 false다. 새 계정을 만들면 사용자별 한도를
새로 받을 수 있다. 현재 사진 AI까지 추가하면 공격 가능한 과금 경로가 늘어난다.

앱의 attestation 설정·기존 계정 처리·인증 메일 완료 안내/토큰 갱신을 준비한 뒤
메트릭을 보고 enforcement를 적용해야 한다. 서버 플래그만 이번에 켜지는 않았다.
[Firebase App Check](https://firebase.google.com/docs/app-check)는 사용자 인증과 별개로
앱/기기 출처를 검증하는 방어다. 위치 정보 자체의 진실성을 보장하는 장치는 아니다.

### P2 — 만료된 촬영 인증의 복구 UX

`useVerification`은 grant가 있으면 만료 시각을 보지 않고 verified로 표시한다.
같은 장소를 다시 열어도 capture store가 grant를 보존한다. 편집을 오래 한 뒤 발행에
실패하면 안내는 나오지만 다시 인증하는 명확한 동선이 부족하다.
만료 타이머·복귀 시 검사와 사진 초안을 보존하는 재인증 동선을 함께 설계해야 한다.

### P2 — 응모 수 집계의 중복·삭제 정합성

`countRaffleEntry`는 이벤트마다 증가시켜 중복 전달을 두 번 셀 수 있다.
`deleteAccount`가 응모 문서를 지울 때 raffle의 `entryCount`는 줄이지 않는다.
응모 문서와 티켓 차감 트랜잭션은 별도로 보호되지만 표시되는 응모 수는 부정확해질 수 있다.
집계 마커를 이용한 중복 방지와 삭제 보정, 또는 집계 쿼리를 사용해야 한다.

### P2 — 프로필 입력 규칙 보강

`firestore.rules`의 사용자 update는 필드 이름은 제한하지만 `avatarUrl`의
형식·허용 출처, `locale`·`profileVisibility`의 enum은 제한하지 않는다.
임의 외부 이미지 URL을 넣으면 공개 프로필을 보는 기기가 그 URL에 요청하게 된다.
아바타와 티켓에서 가져온 프로필 사진의 허용 경로를 먼저 정의하고 규칙 테스트를 추가해야 한다.

### P2 — 크기에 비례하는 전체 조회

`places.listAll`, 티켓 목록, 내 게시글·리뷰 등 여러 경로가 전체 문서를 읽는다.
장소 지도에는 전국 핀이 필요해 단순 반경 필터는 적합하지 않지만, 지도용 작은 projection은
상세 이미지·본문까지 매번 읽는 비용을 줄일 수 있다. 개인 목록은 커서 페이지네이션,
방문 여부는 전체 사진 목록 대신 방문 장소 projection이 적합하다.
서버 탈퇴 역시 사용자 소유 컬렉션을 한 번에 읽는다. 삭제 중 다른 쓰기를 막는 계정 상태와
대량 데이터에서의 재실행 안전성까지 점검할 필요가 있다.

### P2 — 외부 API 지연과 오류 경계

OpenAI·Kakao fetch에 요청별 abort deadline이 없다. 함수 전체 제한에 기대면 앞 호출이
시간을 소진하고 나머지 작업과 재시도 시간이 사라진다. 요청별 제한과 전체 작업의 시간
예산, 오류 분류를 추가할 필요가 있다. 이번에는 외부 유료 API를 호출해 검증하지 않았다.

### P2 — 의존성 보안 업데이트

2026-09-07 로컬 lockfile 기준 검사 결과다. 아래 수치는 중복 의존 경로와 영향 패키지를
포함하므로 서로 다른 취약점 개수나 실제 공격 가능성으로 해석하면 안 된다.

| 대상·명령 | 결과 | 해석 |
| --- | --- | --- |
| 앱 `yarn audit --groups dependencies --json` | high 22, moderate 20, critical 0 | `postcss`, `fast-uri`, `image-size` 등은 상당 부분 Expo/Metro/config 경로. `decode-uri-component`는 navigation 경로에도 포함 |
| 서버 `npm audit --omit=dev --json` | moderate 12, high/critical 0 | `qs`, `uuid` 취약점이 Firebase/Google SDK 의존 경로에 전파 |

앱은 PostCSS 파일 읽기와 이미지 파서 DoS,
서버는 [qs DoS](https://github.com/advisories/GHSA-4mjr-xmp4-gh2g) 등이 보고됐다.
의존성 버전과 호출 경로별로 패치 가능한 범위를 확인해야 한다.
특히 audit의 자동 해결 제안에 Firebase major 다운그레이드가 포함되어
`audit fix --force`는 적용하지 않았다. SDK 업그레이드는 별도의 기기 회귀 검증이 필요하다.

### P3 — 플랫폼·구조·운영 검증

- 웹 실행은 기존 네이버 지도 네이티브 모듈의 `codegenNativeComponent` 오류로 실패했다.
  웹을 지원할 계획이면 `.native`/`.web` 경계를 나누고 브라우저용 대체 화면을 준비해야 한다.
- 두 저장소의 `.github` CI 정의는 찾지 못했다. 외부 CI 운영 여부는 확인하지 않았다.
  타입·린트·편집 수학 테스트·Firebase 에뮬레이터를 기본 검사로 연결하는 것이 다음 단계다.
- `firebase.ts`와 서버 `index.ts`에 여러 도메인이 모여 있다. 대규모 재작성보다
  다음 변경 때 촬영/티켓, 사용자, assistant 단위로 매핑·handler를 분리하면 검토 범위가 작아진다.
- 양쪽 TypeScript 타입은 독립적이고 문서 계약에 의존한다. 공개 DTO의 공유 schema 또는
  callable 계약 테스트를 추가하면 필드 누락을 더 빨리 찾을 수 있다.
- TTL 정의는 `firestore.indexes.json`에 존재한다. 실제 배포 여부, 백업 복구,
  관리자 MFA, 청구 알림 및 운영 로그 대시보드는 이번에 확인하지 않았다.

## AI로 누끼와 배경의 색감을 맞추는 제안

기능 자체는 가능하지만 실제 누끼 이미지와 알파 마스크가 먼저 필요하다.
현재는 그 자산과 선택·합성 기능이 없어서 사진 AI API만 추가해도 사용 가능한 기능이 되지 않는다.

권장 순서는 다음과 같다.

1. 투명 PNG를 불러와 위치·크기를 조절하고, 실제 사진과 같은 좌표계로 합성한다.
2. 누끼가 놓인 주변 영역의 명도·화이트밸런스·채도를 추정하고 누끼에 제한된 보정값을 적용한다.
   강도와 원본 비교를 제공하며 얼굴·의상·알파 윤곽을 유지한다. 이 단계는 기존 Skia로
   기기 내 구현할 수 있어 외부 사진 전송 없이 품질을 먼저 평가할 수 있다.
3. 실제 자산으로 역광·야간·실내 등 테스트 세트를 만든 뒤, 필요하면 AI가 보정 파라미터만
   제안하는 서버 기능을 추가한다. 생성형 재합성을 도입할 경우에는 얼굴/형태 변형을 따로 검증한다.
4. 서버 사용 시 사진 전송 안내, 임시파일 보관 기간, 사용자 쿼터와 App Check,
   타임아웃·원본 복구를 포함한다. 촬영 미리보기는 기기 내 저비용 처리,
   고품질 보정은 촬영 후 처리하는 흐름이 적합하다.

이번에는 AI API·비용·권한 요청을 추가하지 않았다.

## 검증 결과와 남은 실기기 확인

| 검증 | 결과 |
| --- | --- |
| 앱 TypeScript·전체 ESLint·Markdown lint | 통과 |
| 앱 `npm test` | 편집 좌표·실제 Skia 픽셀·PNG 재인코딩·렌즈 이름 처리 통과 |
| iOS·Android `expo export` | 두 플랫폼 Hermes 번들 생성 통과 |
| 서버 TypeScript | 통과 |
| Firestore·Storage·Auth·Functions 에뮬레이터 통합 테스트 | 전부 통과. 실행 기록의 최종 tests/pass 수는 149/149 |
| 네이티브 앱 실행·카메라 렌즈 전환·터치·최종 JPEG 캡처 | 미검증: 이 호스트에 Xcode/시뮬레이터가 없고 실기기 테스트를 수행하지 못함 |
| 웹 앱 실행 | 기존 네이버 지도 모듈 오류로 실패 |
| 프로덕션 배포 | 수행하지 않음 |

기본 Homebrew Node가 누락된 `libsimdjson`을 참조해 실행되지 않아 정상 Node 24로
검사를 수행했다. 서버 선언 런타임은 `functions/package.json`의 Node 22다.
Node 22 배포 환경에서의 확인과 실제 기기 확인은 별도로 남아 있다.

실기기 확인 항목은 권한 거부 후 설정 복귀, 일반/초광각 촬영, 촬영→편집 구도 일치,
모자이크 여러 영역과 스티커를 적용한 뒤 비율 변경, 실행 취소, 최종 JPEG가 미리보기와
일치하는지, 카메라 오류가 티켓 발행으로 넘어가지 않는지다. 공개 범위 변경의 경쟁 조건은
위 P1 후속 작업에 별도 회귀 테스트가 필요하다.
